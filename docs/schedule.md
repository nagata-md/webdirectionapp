# スケジュール自動算出ロジック — schedule.md

> ガントチャートの日付計算がどう決まるかの正（Single Source of Truth）。
> `spec.md`が要件、`computeSchedule.ts`が実装だが、両者の記述が食い違うケース（例：2026-08-28に撤廃した「並行作業人数」）が過去に発生したため、実装と突き合わせた最新の算出ロジックをここに一本化する。
> 実装を変更したら、まずこのファイルを更新してから`spec.md`に反映すること。

対応コード：
- `lib/schedule/computeSchedule.ts`（算出本体）
- `lib/schedule/businessDay.ts`（営業日・非稼働日判定）
- `lib/schedule/groupSequencer.ts`（進行グループのバケット分け）
- `app/(app)/projects/[projectId]/schedule/GanttChart.tsx`（表示）
- `lib/master/constants.ts`（工程名・マスタ型定義）

---

## 1. 基本方針（2026-08-28確定）

**ガントチャートは「想定日数」だけで機械的に開始日・終了日を決める。** 何人・何チームが同時に作業できるかという制約（並行作業人数・作業レーン）はシステムに一切持たない。あるページのある工程は、直前の工程・待機が終わって「着手可能」になった瞬間（レディ時刻）に、他のページ・他工程の状況とは無関係に開始したものとして計算する。

実際に何人でどのページを並行して進めるかは、社内のリソース配分（誰が何を担当するか）で解決する運用上の判断であり、システムはそれを制約条件として扱わない。

> 過去（〜2026-08-27）は「並行作業人数」というマスタ設定値に基づき、工程ごとに同時進行できるページ数を制限する「レーン」の仕組み（`reserveLane()`）が存在した。ページ数が多いプロジェクトでは、あるページ自身の待機時間は短くても、他ページの順番待ちで開始日が大きく後ろ倒しになることがあり、これが「先方チェック待ちが何日も続いているように見える」という誤解を生んでいた。2026-08-28にこの概念自体を撤廃した。

## 2. 用語

| 用語 | 意味 |
|---|---|
| スケジュール工程 | 構成・デザイン・コーディング・CMS構築・テストアップ・公開の6種（`SCHEDULE_PHASES`）。この順序で進む |
| 制作（production） | その工程の初稿を作る作業本体の区間 |
| チェックバック1／チェックバック2 | 先方確認の区間（2校期間対象の4工程のみ、個別に手動編集可） |
| 2校作業（revision） | チェックバック1の指摘を受けた修正作業の区間（自動計算のみ、手動編集不可） |
| バッファ | 制作完了〜次工程着手までの、チェックバック等とは別枠の予備日数 |
| レディ時刻（readyTime） | そのページがその工程に着手できる最も早い日。直前の工程＋待機がすべて終わった時点 |
| 進行グループ | 複数ページをまとめ、同じ起点日から構成工程を開始させるための分類（並行作業人数とは無関係の別概念） |

## 3. 営業日・非稼働日の扱い

- 非稼働日＝定休日（`weekly_off`、曜日番号の配列。既定は土日）＋休日カレンダー（`holidays`、日付＋名称のリスト。祝日は`holidays-jp`公開APIから自動取得可能）。
- すべての日数計算は`shiftBusinessDays(date, n, weeklyOff, holidays)`（`businessDay.ts`）を経由し、非稼働日は一切カウントしない。まず`date`自体を最も近い営業日に正規化してから、営業日ベースで`n`日進める。
- **非稼働日はスケジュールに一切組み込まれない**（要件①）。制作・チェックバック・2校作業・バッファのいずれの区間も、開始日・終了日は必ず営業日になる。

### ガント表示上の非稼働日ルール

- 各セグメント（制作・チェックバック1/2・2校作業・工程間の待機）は、開始日〜終了日の範囲を非稼働日で分断した「連続稼働日の区間（run）」ごとに描画する（`GanttChart.tsx`の`getBusinessDayRuns()`）。非稼働日の列に色が乗ることはない。
- 各セグメントの最終稼働日には、強調用の濃い色のセルを重ねる。この強調セルは常に「最後のrunの最終日」を使う（区間のプロパティ上の`end`をそのまま使うと、暦日ベースで計算された待機区間の`end`が非稼働日に一致するケースがあり、そこに色が乗って見えるバグがあった。2026-08-28修正）。

## 4. 1ページ・1工程あたりの算出式

`computeSchedule.ts`のメインループ（`for (const phase of SCHEDULE_PHASES)`）で、工程ごとに以下を行う。

### 4.1 制作区間

```
start = shiftBusinessDays(readyTime, 0, ...)   // レディ時刻を営業日に正規化した日
end   = shiftBusinessDays(start, duration - 1, ...)
```

`duration`（制作日数）はマスタの単価・工数マスタから、複雑度（S/M/L）と工程に応じて算出する（`phaseDurationDays()`）。

- 構成工程だけは「ワイヤー日数＋コピー日数」を先に合算してから切り上げる（ワイヤー・コピーが不要なページはその分0扱い）。他の工程は単体の日数をそのまま切り上げる。
- どの工程も最低1日は消費する（`Math.max(1, Math.ceil(...))`）。
- CMS構築は`cmsTier`が設定されているページのみ工程自体が存在する。デザイン・コーディングは個別に「なし」に設定すると工程自体をスキップする（readyTimeも進めない）。

手動オーバーライド（`schedule_overrides`）がある場合はマスタ計算を無視し、`overrideStart`/`overrideEnd`をそのまま使う。

### 4.2 制作完了後の待機（次工程のレディ時刻の決め方）

**構成・デザイン・コーディング・テストアップの4工程**（`SECOND_DRAFT_PHASES`）は「2校期間」を持つ：

```
制作完了(end)
  → +1営業日 → チェックバック1（チェックバック日数、standard.checkback）
  → +1営業日 → 2校作業（2校作業日数、standard.secondDraftDays）
  → +1営業日 → チェックバック2（2校チェックバック日数、standard.secondCheckbackDays）
  → +（バッファ日数 + 1）営業日 → 次工程のレディ時刻
```

各セグメントの開始は必ず「前セグメント終了日の翌営業日」（`pushSubSegment()`内の`shiftBusinessDays(cursor, 1, ...)`）。日数が0のマスタ設定の工程はその区間自体が生成されない（ガント上にも表示されない）。

**CMS構築・公開の2工程**は2校期間を持たず、単純合算：

```
制作完了(end) → +（チェックバック日数 + バッファ日数 + 1）営業日 → 次工程のレディ時刻
```

チェックバック1・チェックバック2は個別に手動編集できる仮想セグメント（`${工程名}チェックバック1`等のキーで`schedule_overrides`に保存）。2校作業（revision）は自動計算のみで手動編集の対象外。チェックバック1を編集すると、後続の2校作業・チェックバック2・次工程は（オーバーライドされていない限り）fresh計算で自動的に追従する。

### 4.3 具体例で検算（下層ページL・構成工程）

マスタ設定（2026-08-28時点の実際の値）：

| 項目 | 値 |
|---|---|
| ワイヤー日数（L） | 3日 |
| コピー日数（L） | 2日 |
| 構成のチェックバック日数 | 3日 |
| 構成の2校作業日数 | 2日 |
| 構成の2校チェックバック日数 | 2日 |
| 構成のバッファ日数 | 1日 |

構成の制作日数＝3+2=5日。営業日カレンダーで積むと：

```
Day1〜Day5   : 構成（制作、5営業日）
Day6〜Day8   : チェックバック1（3営業日）
Day9〜Day10  : 2校作業（2営業日）
Day11〜Day12 : チェックバック2（2営業日）
Day13        : バッファ（1営業日）
Day14        : デザイン開始（レディ時刻 = Day12の翌営業日 + バッファ1日 = Day14）
```

「制作5日＋チェックバック3日＋2校作業2日＋2校チェックバック2日＝12日」で次工程に進めたい場合は、**バッファ日数を0に設定する**とDay13にデザインが開始する（Day12の翌営業日）。バッファ日数は「チェックバック等とは別枠で意図的に確保する予備日」であり、0にすれば発生しない。バッファを含めて何日で次工程に進めたいかは、マスタの「バッファ日数」欄で調整する。

## 5. 進行グループとグループ起点日

進行グループは「同じ日に構成工程を開始する複数ページのまとまり」を作るための分類で、並行作業人数とは無関係（§1参照）。

- 表示順1のグループ：プロジェクト開始日を起点とする。
- 表示順2以降のグループ：直前のグループに属する全ページの構成工程の実効終了日（手動オーバーライドがあれば`override_end`、なければ自動計算値）のうち最大値の**翌営業日**を起点とする。
- 同一グループに属する全ページは、構成工程の開始日が常に揃う（グループの起点日＝各ページの構成工程の開始日）。構成工程より後の工程は、ページごとに実際の待機日数の違い（オーバーライドの有無等）に応じて開始日がずれうる。

## 6. 手動オーバーライドとの関係

- 制作区間・チェックバック1・チェックバック2は個別に手動編集できる（`schedule_overrides`）。2校作業は編集対象外。
- ある区間をオーバーライドすると、後続区間はオーバーライドされていない限りfresh計算で自動的に追従する。
- 構成工程の実効終了日が変わり、それが所属グループの構成完了日（最大値）を変化させる場合、次グループ以降を再計算するかどうかを確認ダイアログで選択する。次グループ以降で既にオーバーライドされている区間は、いずれを選んでも変更しない。
