## 1. プロダクト概要

### 背景

Webサイト制作案件（ディレクトリマップ設計・ワイヤー／コピー／デザイン／コーディング・スケジュール管理・見積もり作成）をスプレッドシートで手作業運用しており、属人化・工数増大が発生している。Claude内で作成したHTMLプロトタイプ（v0.5）で設計を検証済み。

### コンセプト

ページ単位の複雑度・要否フラグから見積もりとスケジュールを自動算出し、進行グループ単位で段階的に着手するWebサイト制作案件を、ディレクトリマップ・スケジュール・見積もり・メタ情報を1つの台帳で一元管理するツール。

### 提供価値

- **社内**：ディレクトリマップ・スケジュール・見積もりの手作業を排し、単価マスタ変更や構成変更に強い運用にする。
- **クライアント／外部スタッフ**：見積もり・ディレクトリマップ・スケジュールを、社外秘のマスタ単価を除いた形で安全に共有できる。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| プロジェクト | 1つのWebサイト制作案件。ページ群・スケジュール・見積もりを内包する単位 |
| ページ | ディレクトリマップ上の1ページ（TOP、下層、LP、ブログ等） |
| 複雑度（S/M/L） | ページの制作難易度ランク。標準工数・単価の算出基準 |
| コスト工程 | 単価が発生する作業単位。ワイヤー／コピー／デザイン／コーディング／テストアップ／公開の6種 |
| スケジュール工程 | ガントチャート上の期間単位。構成（ワイヤー＋コピー）／デザイン／コーディング／**CMS構築（Phase 12追加、`cms_tier`を設定したページのみ）**／テストアップ／公開の6種 |
| 進行グループ | 同じタイミングで着手するページの集合。優先度の高い順に段階的に着手する（開始条件は§4.3で確定） |
| マスタ設定 | 全プロジェクト共有の単価・工数・標準待機日数・休日カレンダー・AI連携設定等 |
| チェックバック（CB） | クライアントによる確認・返信待ちの期間。2校期間対象工程（下記）ではCB1・CB2の2回に分かれる |
| バッファ | 自社都合の安全余白期間 |
| 2校期間（Phase 12追加） | 構成／デザイン／コーディング／テストアップの初稿提出後に発生する「チェックバック1→2校作業→チェックバック2」の一連の期間。詳細は§4.5・§4.6 |
| 手動オーバーライド | 自動計算されたガントチャートの日付を人が手動で上書きした状態 |

## 4. 主要機能

### 4.1 プロジェクト管理

| 項目 | 内容 |
|---|---|
| 機能 | プロジェクトの作成・切替・削除・基本情報編集 |
| 保持する基本情報 | クライアント名、プロジェクト名、自社担当者（ディレクター／デザイナー／コーダー等の役割別に複数登録可）、着手日、**サーバー情報リンク**（本番URL・ステージングURL・FTP/CMS管理画面等への外部リンクを複数登録可、ラベル付き）、**Figmaリンク（新規要件・複数登録可、ラベル付き）** |
| バリデーション | プロジェクト名は必須。最後の1件は削除不可 |
| 備考 | サーバー情報リンク・Figmaリンクとも機密情報や実データそのものは保持せず、外部サービス（社内共有ドライブ・Figma）への「リンク」のみを保持する。Figma APIとの自動連携（サムネイル取得・データ同期等）は行わない（要件定義書§4.2のスコープ外方針を維持し、単なる外部リンク登録に留める） |

**プロジェクト一覧・完了/アーカイブ・コピー（2026-08-03新規要件）**：

| 項目 | 内容 |
|---|---|
| フリーワード検索 | プロジェクト名・クライアント名を対象に部分一致検索できる |
| 完了／アーカイブ | プロジェクトを完了（アーカイブ）状態にでき、一覧のデフォルト表示から除外する。「完了済みも表示」トグルで再表示・復元できる |
| 担当者表示 | 一覧の各行に担当者を1名表示する（`project_owners`のディレクターroleを優先、なければ登録順の先頭） |
| コピー機能 | プロジェクトを複製できる。ディレクトリマップ（ページ・進行グループ・親子関係）、自社担当者、サーバー情報リンク／Figmaリンクは複製する。**スケジュールの手動オーバーライド・確定済み見積書（`estimate_versions`）・メタ情報（slug/title/description/keywords/due_date/status）・見積もりの追加項目/備考・外部共有リンク・運用者専用メモは複製しない**（コピー先はまっさらな状態から開始する） |

| 優先度の向き（確定） | 数値が小さいほど優先度が高い（1が最優先）。ディレクトリマップのツリー表示・スケジュール自動生成（§4.5）とも、この昇順で処理する |
| ツリー表示 | 親子関係に基づき階層インデントで表示。ワイヤー・コピーは要否に関わらず常時タグとして表示（「ワイヤー」「コピー」）。CMS構築・スマホ対応メニューを設定したページにも専用タグを表示する |

### 4.3 進行グループ管理

- プロジェクトごとに複数の「進行グループ」を定義できる（例：グループ1＝TOP＋主要下層、グループ2＝事業A、グループ3＝事業B）。

| 項目 | 内容 |
|---|---|
| グループ名 | 任意の名称 |
| 表示順 | グループの着手順序（1, 2, 3…） |
| 所属ページ | ディレクトリマップ上の各ページに1つの進行グループを割り当てる（未設定ページは表示順1のデフォルトグループ扱い） |

**開始条件（確定・要件定義書§6.3の未決定事項#1への回答）**：

- **表示順1のグループ**：プロジェクト開始日を起点とする。
- **表示順2以降のグループ（2026-08-03改訂）**：直前の表示順のグループに属する全ページの「構成」（スケジュール工程）が完了した日の**翌営業日**を起点とする（土日・休日をまたぐ場合は次の営業日まで飛ばす）。「構成完了日」は、そのグループに属する全ページの構成工程終了日のうち最大値。※旧仕様（完了日当日を起点、オフセットなし）から変更。
- **構成工程の並行作業人数制限は適用しない（2026-08-03確定）**：同一進行グループ内の複数ページは、構成工程の並行作業人数（マスタ設定）の値に関わらず、常にグループの起点日に全ページが同日着手する。並行作業人数の制限は構成より後の工程（デザイン以降）にのみ適用される。

> ⚠️ 実装上の注意：グループ2以降の起点は前グループの計算結果に依存するため、進行グループは表示順に従って**逐次計算**する（並列計算不可）。あるグループのページ構成・複雑度を変更すると、後続グループ全体の再計算が必要になる。

**手動オーバーライドとの相互作用（確定）**：

- グループの「構成完了日」（＝次グループの起点）は、そのグループに属する全ページの構成工程の**実効終了日**（手動オーバーライドがあれば`override_end`、なければ自動計算値`computed_end`）の最大値とする。つまり手動オーバーライドは次グループの起点計算にそのまま反映される（オーバーライドされた日付が「本当の完了日」として扱われる）。
- あるページの構成工程の終了日をオーバーライドし、それが所属グループの構成完了日（最大値）を変化させる場合、次グループ以降の自動計算区間（オーバーライドされていない区間のみ）を再計算するかどうかを、§4.6の後続工程追従ダイアログと同様の確認ダイアログで選択させる（「次グループ以降の自動計算区間を再計算する」／「このページの区間だけ変更する（次グループ以降は今のまま据え置く）」）。
- 上記いずれを選んだ場合も、次グループ以降で**既にオーバーライドされている区間**は変更しない（§4.6の原則を維持。既存オーバーライドは常に自動再計算の対象外）。

### 4.5 スケジュール自動生成ロジック

1. §4.3の開始条件に基づき、進行グループを表示順に沿って逐次処理し、各ページの初期レディ時刻（工程着手可能日＝所属グループの起点日）を決定する。
2. ページは優先度順に処理し、スケジュール工程（構成→デザイン→コーディング→CMS構築→テストアップ→公開）ごとに、工程別の並行作業レーン（プロジェクトで設定した並行作業人数）に空きが出次第割り当てる。ただし**構成工程のみ例外**で、並行作業人数の制限を適用せず、同一進行グループの全ページが常にグループ起点日に同日着手する（§4.3）。
3. 各工程の制作日数は、該当ページの複雑度・ワイヤー/コピー要否に基づきマスタから算出し、営業日ベースで日数を積む。
4. 制作完了後、マスタの標準待機日数を営業日で加算し、次工程のレディ時刻とする。構成・デザイン・コーディング・テストアップの4工程は「チェックバック＋2校作業日数＋2校チェックバック日数＋バッファ」、CMS構築・公開の2工程は「チェックバック＋バッファ」を加算する（2校期間については後述）。
5. 全ページの最終工程（公開）完了日のうち最大値をプロジェクト全体の完了予定日とする。

**端数日の扱い（確定）**：単価マスタの日数は0.5日単位で入力できるが、ガントチャート上の開始日・終了日は暦日（丸日）単位のため、スケジュール工程ごとに合計してから切り上げる（構成はワイヤー＋コピーの日数を先に合算してから切り上げる。他の工程は単体で切り上げる）。工程間で端数を繰り越すことはしない。

**2校期間（2026-08-03新規要件、同日改訂）**：構成・デザイン・コーディング・テストアップの各工程は、提出（初稿）後の待機期間を「チェックバック1（既存のチェックバック日数）→2校作業（新規の2校作業日数）→チェックバック2（新規の2校チェックバック日数）→バッファ（既存）」の順で構成する。2校作業日数・2校チェックバック日数はマスタ設定でスケジュール工程ごとに個別設定できる（既定値の目安：各3日）。CMS構築・公開の2工程には適用しない（従来通りチェックバック＋バッファのみ）。なお、進行グループの起点計算（§4.3の「構成完了日」）は初稿提出日（2校期間を含まない`end`）を基準とし、2校期間は同一ページ内の次工程への影響のみに留める。

ガント上の表現（2026-08-03改訂）：チェックバック1・2校作業・チェックバック2はそれぞれ独立した区間としてガントに描画する。制作（初稿・2校作業）は工程色（青系等）、チェックバック1・2はピンク系の色で表示し、「制作→CB1→2校作業→CB2」の順に並ぶ。チェックバック1・2は制作工程と同様にバーをクリックして個別に手動編集できる（内部的には`schedule_overrides`に`${工程名}チェックバック1`／`${工程名}チェックバック2`という仮想の工程キーで区間を保存する）。2校作業区間自体は現時点では自動計算のみで手動編集の対象外とする。チェックバック1を編集して終了日が変わると、2校作業・チェックバック2・次工程はオーバーライドされていない限りfresh計算により自動的に追従する。

### 4.6 ガントチャートの表示・手動編集

| 項目 | 内容 |
|---|---|
| 表示 | ページ単位の行×時系列のカレンダー型ガントチャート（Phase 12、日付を1日ずつ列にしたグリッド）。工程ごとに色分けし、制作期間と待機期間を区別して表示する。各区間の最終日は少し濃い色で強調表示する（2026-08-03追加）。区間が週末・休日をまたぐ場合、非稼働日の列は色を塗らない（稼働日のみ着色し、休んでいる間も作業しているように見えないようにする、2026-08-03追加） |
| サマリー表示（2026-08-03追加） | チャート上部に、プロジェクト全体の「公開予定日」（全ページの最終工程完了日のうち最大値）と「作業日数」（プロジェクト開始日〜公開予定日の営業日数）を大きく表示する。ページ単位の個別値は表示しない |
| ページ単位の最終工程の表示名（2026-08-03改訂） | ページ単位の最終工程は画面上「作業完了」と表示する（内部データ上のキーは従来通り"公開"のまま）。サイト全体は全ページが揃って初めて公開されるため、実際の公開日（全ページの作業完了日のうち最大値）を1日だけ全ページの行に黒色のセルとして共通表示する |
| チェックバック・バッファの可視化（2026-08-03追加、同日改訂） | 2校期間対象の4工程（構成／デザイン／コーディング／テストアップ）はチェックバック1・2校作業・チェックバック2をそれぞれ個別の区間として表示する（チェックバック1・2はピンク系、2校作業は制作と同じ工程色）。CMS構築・公開の2工程、および2校期間対象工程の残りのバッファ待機は、従来通り工程間の汎用の待機区間（ピンク系）としてまとめて表示する。各区間の最終日は同様に少し濃い色にする |

| 変更履歴 | 誰が・いつ・どの区間を手動編集したかの履歴を最低限のログとして保持する |
| グループ起点への影響 | 「構成」工程のオーバーライドが所属グループの完了日（＝次グループの起点）を変化させる場合の挙動は§4.3で規定する（次グループ以降の自動計算区間を再計算するか確認ダイアログで選択、既存オーバーライドは対象外） |

### 4.7 見積もり

**表示順（確定）**：画面・CSV・PDFとも、上から「①ディレクション費 → ②ページ別コスト（制作関連） → ③追加項目（素材費〜値引き、手入力）」の順で表示する。合計計算自体は加算なので順序に依存しないが、体裁上はこの並びを正とする。

| 項目 | 内容 |
|---|---|
| ①ディレクション費 | 月額ディレクション費 ×（スケジュール期間の暦月数） |
| ②ページ別コスト | 複雑度別単価 ×（ワイヤー/コピー要否）＋CMS構築費（該当ページのみ）＋スマホ対応メニュー費（該当ページのみ） |
| ③追加項目（新規要件） | プロジェクトごとに「項目名・金額」の手入力行を任意の件数追加できる。素材費等の追加費用はプラス、値引きはマイナスの金額で入力する（正負自由入力、種別の選択欄は設けない） |
| 合計 | ディレクション費＋制作費小計＋追加項目の合計＝税抜合計、税込合計（消費税率はマスタ設定で変更可能） |
| 出力 | 画面表示に加え、CSV等の形式でエクスポート可能（①→②→③の順、追加項目も内訳に含める） |
| バージョン管理・PDF発行 | 「確定してPDF発行」操作で押下時点の計算結果を凍結・発行する。詳細は§4.11 |
| **表示タブ（Phase 12新規）** | 「詳細見積もり」「集計見積もり」の2タブで切り替える。**詳細**：ページ単位・コスト工程単位の内訳をすべて表示。**集計**：TOP関連のみページ単位で1式個別表示、それ以外はコスト工程×複雑度で集計し、CMS構築費は個別行、テストアップ＋公開は「テスト検証」として1行に集約する（**合計が0円の場合はこの行を非表示にする**）。両タブは同一の入力から算出するため、小計・合計は必ず一致する |
| **備考欄（Phase 12新規）** | プロジェクト単位で自由記述の備考を入力・保存できる（`projects.estimate_remarks`）。画面・PDFの見積もり内訳の下部に表示する |

### 4.9 AIによるメタ情報一括生成（新規要件）

ページ数が多い案件でSEOメタ情報（スラッグ・TITLE・ディスクリプション・キーワード）を手入力する手間を削減する。

| 項目 | 内容 |
|---|---|
| 実行画面 | メタ情報・進行管理画面に「AI一括生成」パネルを設置 |
| 入力 | サイト全体の方向性・トーンを指示する自由記述の指示文（例：「BtoB向け、堅めのトーン、地域名を意識したキーワードを入れる」）。ページごとの個別入力は不要——ディレクトリマップに登録済みの全ページ情報（ページ名・種別・親子階層・優先度）を自動的に読み込み、指示文と合わせてプロンプトに含める |
| 指示文の記憶（新規要件） | 画面を開いた際、指示文欄には当該プロジェクトで直近に使用した指示文を初期値として表示する（同じ方向性を毎回入力し直す手間を省く。生成ログ（下記）の最新1件から取得し、専用の保存項目は設けない） |
| 生成対象の選択 | 「未入力ページのみ」（デフォルト）／「全ページ（既存値も上書き）」を切り替え可能。デフォルトは未入力のみとし、手動で書いたメタ情報を誤って上書きしない（§4.6の手動オーバーライド尊重の方針と一貫させる） |
| 実行 | 「生成」ボタン押下でClaude APIに1回のリクエストを送り、各ページの slug / title / description / keywords を構造化出力（JSON）として受け取る |
| レビュー | 生成結果は即保存せず、ページ別の編集可能なプレビュー一覧に表示する。内容を確認・修正した上で「反映」ボタンで台帳に保存する |
| ログ | 誰が・いつ・どんな指示文で・何ページ分生成したかを最低限記録する（監査目的ではなく、後から経緯を追える程度） |
| 設定 | Claude APIキー・使用モデルはマスタ設定で管理（§4.4） |
| スコープ外 | ページ本文・ワイヤー・コピー・デザインの自動生成は行わない（要件定義書§4.2のスコープ外方針を踏襲。あくまでSEOメタ情報のみ） |

> ⚠️ 要相談：Claude APIの利用コスト（月間見込み回数・トークン量）は実装後に実測し、想定利用規模に対して妥当かを確認する。

### 4.10 外部共有機能（公開URL発行）

社内マスタ（単価・工数表）を除いた、基本情報・見積もり・ディレクトリマップ・スケジュール・メタ情報をクライアントや外部スタッフに閲覧共有できる機能。

| 項目 | 内容 |
|---|---|
| 発行単位 | プロジェクト単位で共有URLを発行する |
| 公開範囲（デフォルト） | 見積もり（総額・ページ別内訳）、ディレクトリマップ（ページツリー）、スケジュール（ガントチャート）。マスタ設定は常に非公開 |
| 公開範囲（除外を推奨する内部運用項目） | ページの個別費用の内訳算出根拠、優先度、進行グループの並行作業人数設定、休日カレンダー、内部担当者名、進捗ステータス（社内管理用の詳細）は、含めた各セクション内で常に非表示とする（個別のON/OFFトグルは設けない）。共有作成時にON/OFF選択できるのは①基本情報②見積もり③ディレクトリマップ④スケジュール⑤メタ情報の5セクション単位（基本情報は下記2段階） |
| 基本情報セクション（新規要件） | 2段階の公開レベルから一方を選んで含める。**①秘密情報なし**：プロジェクト名・クライアント名・着手日のみを表示。**②秘密情報あり（開発サポート者向け）**：①に加えて自社担当者・サーバー情報リンク・Figmaリンクを含む全項目を表示する。両方を同時に含めることはできない（発行画面でどちらか一方のみ選択） |
| 表示モード | 参照専用（編集不可） |
| 共有モードの種類 | **①ライブ**：含まれる全セクションが常に最新のプロジェクトデータを反映する閲覧用URL。**②見積バージョン紐付け（`estimateVersion`）**：見積もりセクションのみ、指定した発行済み`estimate_versions`（§4.11）の凍結データを表示する。ディレクトリマップ・スケジュールのセクション（含めている場合）は、このモードでも常に最新（ライブ）のデータを表示する——**凍結されるのは見積金額のみ** |
| デフォルト選択ロジック（確定） | 共有作成画面で見積もりセクションを含む場合、デフォルトは**見積バージョン紐付け**とし、その場でプロジェクトの発行済み`estimate_versions`一覧から紐付けるバージョンを選択させる（未発行の場合は「先に見積もり画面でPDF発行してください」と案内し、発行するまで`estimateVersion`モードは選択不可とする）。見積もりセクションを含まない（スケジュール／ディレクトリマップのみ）場合、デフォルトは**ライブ** |
| マスタ単価変更時の影響（確定） | ライブモードの見積もりセクションは常に最新のマスタ単価を反映する（仕様通りの挙動であり、これ自体は不具合ではない）。マスタの単価・工数を変更して保存する際、影響を受ける「有効なライブ共有リンク（失効・期限切れでなく、見積もりセクションを含むもの）」が存在する場合は、保存前に確認ダイアログで対象件数・プロジェクト名を表示する（例：「この変更は現在有効な3件のライブ共有（見積もり公開中）の表示金額に影響します。続行しますか？」）。**見積バージョン紐付けモードの共有リンクは、参照する`estimate_versions`が発行時点で凍結されているためこの警告の対象外であり、マスタ変更の影響を一切受けない**（§4.11） |
| セキュリティ（確定） | URLは推測不可能なランダムトークンを含む。パスワードは任意設定（必須化はしない。案件の機密度に応じて発行者が都度判断する）。有効期限は発行時に日数指定（デフォルト90日、発行者が変更可能）。発行者はいつでも失効できる |
| アクセスログ | 誰が発行したか、閲覧回数・最終閲覧日時を記録する |
| 複数発行 | 1プロジェクトに対し用途別に複数の共有URLを発行・個別管理できる |
| ダウンロード（Phase 12で追加） | メタ情報セクションを含む場合、開発者向けCSVをダウンロードできる。見積もりセクションを含み`estimateVersion`モードの場合、発行済み見積書PDFをダウンロードできる（§4.11） |

> ~~⚠️ 要相談：共有URL発行時のデフォルト選択モード~~ → 解決：見積もりセクションの有無で自動判定する（上表参照）。
> ~~⚠️ 要相談：パスワード設定の必須化の是非~~ → 解決：必須化しない。任意設定とし、発行者の判断に委ねる（上表参照）。

### 4.11 見積書PDF出力・バージョン管理（新規要件）

見積もりを正式な書面として発行し、発行後はマスタ単価が変更されても内容が変わらないようにする。

| 項目 | 内容 |
|---|---|
| 発行操作 | 見積もり画面（§4.7）に「確定してPDF発行」ボタンを設置。押下時点の計算結果（ディレクション費・ページ別コスト・**追加項目（素材費・値引き等）**・小計・消費税・合計）を`estimate_versions`（§6）として凍結保存し、同時にPDFを生成する |
| 見積書の体裁 | 見積番号（自動採番）・発行日・有効期限（マスタ設定の`estimate_validity_days`から算出。既定30日）・御中（クライアント名）・件名（プロジェクト名）・**①ディレクション費 → ②ページ別内訳 → ③追加項目の内訳（項目名・金額）の順**・小計／消費税／合計・自社情報（会社名・住所・電話番号・角印画像）を含む正式な体裁とする（表示順は§4.7参照） |
| 生成方式 | `@react-pdf/renderer`によるPDFネイティブ生成（Vercelのサーバーレス関数上で実行） |
| 発行元情報 | マスタ設定に発行元情報欄（会社名・住所・電話番号・角印画像）を追加する（§4.4・§6） |
| バージョン一覧 | 見積もり画面に、そのプロジェクトで発行済みの`estimate_versions`を一覧表示する（見積番号・発行日・有効期限・合計金額・発行者）。各行からPDFを再ダウンロードできる |
| 不変性（確定） | 発行済みの`estimate_versions`はイミュータブルとして扱う。発行後にマスタの単価・工数・消費税率を変更しても、既存の`estimate_versions`のデータ・PDFの内容は一切変わらない |
| 出力範囲（Phase 12で変更） | PDF発行・再ダウンロードは社内の見積もり画面から行える。外部共有閲覧画面（§4.10）からも、`estimateVersion`モード（発行済みPDFが存在する場合）に限りPDFダウンロードを提供する。`live`モードは都度PDF生成の仕組みを持たないため対象外（画面上での金額閲覧のみ） |
| 外部共有との連携 | 外部共有リンクのモード`estimateVersion`（§4.10）で発行済みバージョンのいずれかを指定すると、その共有リンクの見積もりセクションは指定バージョンの凍結データを表示し、発行済みPDFをダウンロードできる |

## 8. 非機能要件

- ログイン認証必須（単価情報を含むため）。Supabase Auth + Google OAuth、ドメイン制限。
- チーム共有データ（マスタ・プロジェクト一覧）は同一組織内の全メンバーがアクセス可能。編集権限の細分化は次フェーズで検討。
- レスポンシブ対応は必須としない（社内利用のデスクトップ運用を主とする）が、タブレット幅での閲覧に配慮する。
- データのエクスポート（CSV等）を各画面に用意する。
- 外部共有URLは推測不可能なトークンを用い、パスワード設定・有効期限・失効操作を機能として備える。共有URL経由のアクセスは編集権限を一切持たない参照専用とする。
- Claude APIキーはマスタ設定内で暗号化して保存し、画面上には再表示しない（登録・更新のみ可能。§6の列単位除外ルールを参照）。
- **タイムゾーン（確定）**：営業日計算（休日カレンダー・チェックバック・バッファの日数加算、進行グループの起点計算等）はすべて **JST（Asia/Tokyo）** を前提とする。Vercel関数・Supabaseのサーバー既定タイムゾーンはUTCのため、日付はタイムゾーンなしの`date`型（`YYYY-MM-DD`文字列）として一貫して扱い、タイムゾーン変換を伴う`Date`オブジェクトでの日時演算は避ける（UTCとのずれによる1日ズレを防止する。サーバー情報管理アプリでも同種のバグが発生し、`Asia/Tokyo`固定で解消した実績あり）。「今日」の判定が必要な箇所（起算日確定等）も、サーバーのUTC時刻からJSTへ変換した上で日付を確定する。
- 発行済み見積書PDF・角印画像はSupabase Storageの非公開バケットに保存し、ダウンロードは認証済みユーザー限定の署名付きURL経由とする（外部共有閲覧画面からは提供しない、§4.11）。
- 想定同時利用人数・データ量（案件数・ページ数の上限目安）は実装前にヒアリングして確定する。
