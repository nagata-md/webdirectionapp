# 制作進行オートメーター 要件定義書

version 0.2 / 起票日：2026-08-01（初版）／更新：外部共有機能を追加
起票者：ながた（マーケティングデパートメント）

---

## 1. 文書の目的

本書は、Webサイト制作案件（ディレクトリマップ設計・ワイヤー／コピー／デザイン／コーディング・スケジュール管理・見積もり）を自動化するWebアプリケーションを開発するための要件定義書である。Claude内で作成したHTMLプロトタイプ（v0.5）で検証済みの設計を土台とし、実務ヒアリングで判明した追加要件を反映する。

本書の読者はClaude Code等での実装担当者を想定する。技術スタック（フロントエンド／バックエンド／DB／ホスティング）は本書では規定せず、実装フェーズで別途決定する。

---

## 2. 背景・課題

- ディレクトリマップ作成、ワイヤー・コピー・デザイン・コーディングのスケジュール作成、見積もり作成をスプレッドシートで手作業運用しており、属人化・工数増大が発生している。
- 実際の運用スプレッドシートを分析した結果、以下の実務要件が判明している。
  - ページ単位でワイヤー・コピーの要否が異なる（テンプレート流用ページは工数が発生しない）
  - ページ単位の個別費用（CMSカスタム費、フォーム構築費等）が標準単価とは別に発生する
  - スケジュールは土日・祝日・自社/クライアント定休日を除いた営業日ベースで組まれる
  - 工程は「構成→デザイン→コーディング→テストアップ→公開」で運用されている
  - 全ページが一斉に進行するのではなく、優先度の高いページ（TOPなど）から着手し、一定のグループ単位で段階的に進行する
  - ディレクション費用は制作費に対する掛け率ではなく、スケジュール期間の**月額課金**である
  - URLスラッグ・TITLE・ディスクリプション・キーワード等のSEOメタ情報や、進捗ステータス・納品予定日の管理も同じページ台帳上で行いたい

- 上記をプロトタイプで検証したところ設計の妥当性は確認できたが、以下の実務上の不足が判明した。
  1. 自動生成したガントチャートを、先方都合・遅延等に応じて**手動で修正**できない
  2. スケジュールは「ページ優先度＋工程別並行作業人数」だけで組まれており、**進行グループ単位の段階着手**を表現できない
  3. プロジェクトの基本情報（クライアント名・プロジェクト名・担当者・サーバー情報リンク）を格納する欄がない

本書はこれらを反映した本実装の要件を定義する。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| プロジェクト | 1つのWebサイト制作案件。ページ群・スケジュール・見積もりを内包する単位 |
| ページ | ディレクトリマップ上の1ページ（TOP、下層、LP、ブログ等） |
| 複雑度（S/M/L） | ページの制作難易度ランク。標準工数・単価の算出基準 |
| コスト工程 | 単価が発生する作業単位。ワイヤー／コピー／デザイン／コーディング／テストアップ／公開の6種 |
| スケジュール工程 | ガントチャート上の期間単位。構成（ワイヤー＋コピー）／デザイン／コーディング／テストアップ／公開の5種 |
| 進行グループ | 同じタイミングで着手するページの集合。優先度の高い順に段階的に着手する |
| マスタ設定 | 全プロジェクト共有の単価・工数・標準待機日数・休日カレンダー等の設定 |
| チェックバック（CB） | クライアントによる確認・返信待ちの期間 |
| バッファ | 自社都合の安全余白期間 |
| 手動オーバーライド | 自動計算されたガントチャートの日付を人が手動で上書きした状態 |

## 4. 対象範囲

### 4.1 スコープ内
- ディレクトリマップ作成・管理
- 進行グループ設定
- マスタ設定（単価・工数・標準待機日数・休日カレンダー・並行作業人数・月額ディレクション費）
- ページ単位のスケジュール自動生成（営業日ベース）
- ガントチャートの手動編集・オーバーライド管理
- 見積もり自動算出
- メタ情報・進行管理（SEO情報、進捗ステータス）
- プロジェクト基本情報管理（クライアント名・担当者・サーバー情報リンク）
- 外部共有機能（見積もり・ディレクトリマップ・スケジュールの公開URL発行、マスタは非公開）
- チーム共有（複数メンバーが同一マスタを参照し、プロジェクト単位で独立管理）

### 4.2 スコープ外（本フェーズでは対象外）
- フォーム自動返信メールの文言管理
- 実際のワイヤーフレーム・コピー・デザインデータそのものの生成（AIによる制作物自動生成は行わない）
- 外部ツール（Figma、WordPress管理画面等）との自動連携
- 請求書発行・会計連携

## 5. 全体方針

- **マルチプロジェクト**：1つのマスタ設定を複数プロジェクトが共有する。プロジェクトはユーザーが自由に作成・切替・削除できる。
- **チーム共有**：マスタ設定・プロジェクトデータはチームメンバー全員が閲覧・編集可能とする（本フェーズでは詳細な権限分離は行わない。将来的に編集権限の分離は要検討）。
- **単価情報の機密性**：単価マスタは社外秘のため、アクセス制御（ログイン必須化）を非機能要件として必須とする。
- **データの永続化**：プロトタイプはブラウザ内蔵ストレージで検証したが、本実装では正式なデータベースを用いる。

## 6. 機能要件

### 6.1 プロジェクト管理

| 項目 | 内容 |
|---|---|
| 機能 | プロジェクトの作成・切替・削除・基本情報編集 |
| 保持する基本情報 | クライアント名、プロジェクト名、自社担当者（ディレクター／デザイナー／コーダー等の役割別に複数登録可）、着手日、サーバー情報リンク（本番URL・ステージングURL・FTP/CMS管理画面等への外部リンクを複数登録可、リンクにはラベルを付与） |
| バリデーション | プロジェクト名は必須。最後の1件は削除不可 |
| 備考 | サーバー情報リンクは機密情報を直接保存せず、あくまで社内共有ドライブ等への「リンク」を保持する方針とする（本アプリ内に認証情報を保持しない） |

### 6.2 ディレクトリマップ

| 項目 | 内容 |
|---|---|
| 機能 | ページの追加・編集・削除、親子階層設定、ツリー表示 |
| ページ項目 | ページ名、種別（TOP/下層/LP/ブログ/その他）、複雑度（S/M/L）、親ページ、ワイヤー要否、コピー要否、個別費用（円）、**進行グループ**、優先度 |
| ツリー表示 | 親子関係に基づき階層インデントで表示。ワイヤー／コピー不要ページ、進行グループはバッジで視覚化 |

### 6.3 進行グループ管理（新規要件）

- プロジェクトごとに複数の「進行グループ」を定義できる（例：グループ1＝TOP＋主要下層、グループ2＝事業A、グループ3＝事業B）。
- グループには以下を設定する。

| 項目 | 内容 |
|---|---|
| グループ名 | 任意の名称 |
| 表示順 | グループの着手順序 |
| 開始条件 | 案A：プロジェクト開始日からの営業日オフセット（例：グループ2はプロジェクト開始10営業日後）／案B：前グループの特定工程完了を起点とした相対オフセット |
| 所属ページ | ディレクトリマップ上の各ページに1つの進行グループを割り当てる（未設定ページはデフォルトグループ扱い） |

> **要確認事項**：開始条件は案Aと案Bのどちらを採用するか実装前に決定する。プロトタイプ検証時点では、実運用スケジュールが「固定営業日オフセット」に近い挙動だったため、**案Aを初期実装の推奨仕様とする**。

- スケジュール計算時、各ページの初期レディ時刻（工程着手可能日）は「プロジェクト開始日＋所属グループの開始オフセット」を基準とし、そこから6.5の工程別レーン割当ロジックに従う。

### 6.4 マスタ設定（チーム共有）

| 項目 | 内容 |
|---|---|
| 単価・工数マスタ | 複雑度（S/M/L）×コスト工程（ワイヤー／コピー／デザイン／コーディング／テストアップ／公開）ごとの標準日数・単価 |
| 標準待機日数 | スケジュール工程（構成／デザイン／コーディング／テストアップ／公開）ごとのチェックバック日数・バッファ日数 |
| 休日カレンダー | 祝日・特別休業日のリスト（日付・名称、追加/削除可） |
| 定休日 | 曜日指定による毎週の除外日（デフォルト：土日） |
| 月額ディレクション費 | 円／月。プロジェクトのスケジュール期間（開始月〜完了月の暦月数）×月額で見積もりに計上 |
| 工程別並行作業人数のデフォルト値 | プロジェクト作成時の初期値として使用（プロジェクトごとに上書き可） |

### 6.5 スケジュール自動生成ロジック

1. 各進行グループの開始オフセットに基づき、ページごとの初期レディ時刻を決定する。
2. ページは優先度順に処理し、スケジュール工程（構成→デザイン→コーディング→テストアップ→公開）ごとに、工程別の並行作業レーン（プロジェクトで設定した並行作業人数）に空きが出次第割り当てる。
3. 各工程の制作日数は、該当ページの複雑度・ワイヤー/コピー要否に基づきマスタから算出し、営業日ベースで日数を積む。
4. 制作完了後、マスタの標準待機日数（チェックバック＋バッファ）を営業日で加算し、次工程のレディ時刻とする。
5. 全ページの最終工程（公開）完了日のうち最大値をプロジェクト全体の完了予定日とする。

### 6.6 ガントチャートの表示・手動編集（新規要件）

| 項目 | 内容 |
|---|---|
| 表示 | ページ単位の行×時系列のガントチャート。工程ごとに色分けし、制作期間と待機期間を区別して表示 |
| 手動編集 | 各ページ・各工程の開始日／終了日をドラッグ操作または日付入力で直接変更できる |
| オーバーライド管理 | 手動編集された工程区間は「手動オーバーライド」フラグを立てて記録する。以降、マスタ単価・工数の変更やページ構成の変更があっても、**オーバーライド済みの区間は自動再計算で上書きしない** |
| 連動編集 | 手動編集によりあるページのある工程が後ろ倒しになった場合、同一ページの後続工程（その工程より後）を追従して自動的に後ろ倒しするかどうかを、編集時に確認ダイアログで選択できるようにする（「このページの後続工程も追従させる」／「この区間だけ変更する」） |
| リセット | 手動オーバーライドを解除し、自動計算値に戻す操作を用意する（ページ単位・工程単位の両方で可能とする） |
| 変更履歴 | 誰が・いつ・どの区間を手動編集したかの履歴を最低限のログとして保持する（監査ログとしての厳密な実装までは本フェーズでは求めない） |

### 6.7 見積もり

| 項目 | 内容 |
|---|---|
| ページ別コスト | 複雑度別単価 ×（ワイヤー/コピー要否）＋個別費用 |
| ディレクション費 | 月額ディレクション費 ×（スケジュール期間の暦月数） |
| 合計 | 制作費小計＋ディレクション費＝税抜合計、税込合計（消費税率は設定可能とする） |
| 出力 | 画面表示に加え、CSV等の形式でエクスポート可能とする |

### 6.8 メタ情報・進行管理

| 項目 | 内容 |
|---|---|
| 管理項目 | URLスラッグ、TITLE、ディスクリプション、キーワード、優先度、納品予定日、進捗ステータス（未着手／構成中／デザイン中／コーディング中／テスト中／公開済） |
| 連動 | ディレクトリマップのページと1対1で連動する（同一ページIDを参照） |

### 6.9 外部共有機能（公開URL発行）（新規要件）

社内マスタ（単価・工数表）を除いた、見積もり・ディレクトリマップ・スケジュールをクライアントや外部スタッフに閲覧共有できる機能。

| 項目 | 内容 |
|---|---|
| 発行単位 | プロジェクト単位で共有URLを発行する |
| 公開範囲（デフォルト） | 見積もり（総額・ページ別内訳）、ディレクトリマップ（ページツリー）、スケジュール（ガントチャート）。**マスタ設定は常に非公開** |
| 公開範囲（除外を推奨する内部運用項目） | ページの個別費用の内訳算出根拠、優先度、進行グループの並行作業人数設定、休日カレンダー、内部担当者名、進捗ステータス（社内管理用の詳細）は、デフォルトで非表示とする。共有時にセクション単位でON/OFFを選択できるようにする |
| 表示モード | 参照専用（編集不可）。共有URL経由のアクセスでは一切の編集操作を行えない |
| 共有モードの種類 | **①ライブ共有**：常に最新のプロジェクトデータを反映する閲覧用URL。スケジュール変更や進捗共有を継続的に行う用途向け。<br>**②提出用スナップショット**：発行した時点のデータを凍結し、以後プロジェクト側を編集してもスナップショットの内容は変わらない。正式な見積提出・証跡保存用途向け（元のスプレッドシートに「【提出】」という命名がある通り、提出時点の内容固定は実務上の要件と判断） |
| セキュリティ | URLは推測不可能なランダムトークンを含む。任意でパスワードを設定できる。有効期限を設定できる（デフォルト例：発行から90日）。発行者はいつでも共有を失効（無効化）できる |
| アクセスログ | 誰が発行したか、閲覧された回数・最終閲覧日時を記録する（詳細な閲覧者トラッキングまでは本フェーズでは求めない） |
| 複数発行 | 1プロジェクトに対し、用途別（クライアント提出用／外部スタッフ進行共有用等）に複数の共有URLを発行・個別管理できる |

## 7. データモデル（エンティティ定義）

```
Master（チーム共有・1件のみ）
- rates: 複雑度 × コスト工程 → { days, cost }
- standards: スケジュール工程 → { checkback, buffer }
- weeklyOff: 曜日番号の配列
- holidays: [{ date, label }]
- directionMonthlyRate: number
- defaultParallelByPhase: スケジュール工程 → number

Project
- id, clientName, projectName, owners: [{ role, name }]
- serverLinks: [{ label, url }]
- startDate
- parallelByPhase: スケジュール工程 → number
- groups: [{ id, name, order, startOffsetDays }]
- pages: Page[]

Page
- id, name, type, complexity, parentId
- wireNeeded, copyNeeded, extraCost
- groupId
- priority
- slug, title, description, keywords, dueDate, status

ScheduleOverride（手動編集の記録）
- pageId, phaseKey
- overrideStart, overrideEnd
- cascadeFollowing: boolean
- editedBy, editedAt

ShareLink（外部共有）
- id, projectId, token（推測不可能なランダム文字列）
- mode: 'live' | 'snapshot'
- snapshotData（modeがsnapshotの場合、生成時点の見積もり・ディレクトリマップ・スケジュールのデータを保持）
- includeSections: { estimate: boolean, directoryMap: boolean, schedule: boolean, meta: boolean }
- passwordHash（任意）
- expiresAt
- revoked: boolean
- createdBy, createdAt
- viewCount, lastViewedAt
```

## 8. 非機能要件

- ログイン認証必須（単価情報を含むため）。認証方式は実装フェーズで決定する。
- チーム共有データ（マスタ・プロジェクト一覧）は同一組織内の全メンバーがアクセス可能とする。将来的な編集権限の細分化（マスタは管理者のみ編集可、等）は次フェーズで検討する。
- レスポンシブ対応は必須としない（社内利用のデスクトップ運用を主とする）が、タブレット幅での閲覧に配慮する。
- データのエクスポート（CSV等）を各画面に用意する。
- 外部共有URLは推測不可能なトークンを用い、パスワード設定・有効期限・失効操作を必須機能とする。共有URL経由のアクセスは編集権限を一切持たない参照専用とする。
- 想定同時利用人数、データ量（案件数・ページ数の上限目安）は実装前にヒアリングして確定する。

## 11. 参考：検証済みプロトタイプ

本要件はClaude上で作成したHTMLプロトタイプ（v0.1〜v0.5）で以下を検証済み。
- 複雑度別単価マスタに基づく見積もり自動計算
- 営業日ベース（祝日・定休日除外）のスケジュール計算
- ページ単位・工程別レーン制約に基づく資源配分スケジューリング
- ワイヤー／コピーのページ単位要否フラグと個別費用の反映
- 月額ディレクション費の暦月カウント計算

実装時は上記ロジックをそのまま移植可能。ソースコードは別途プロトタイプファイル（site-planner-v5.html）を参照のこと。
